# Solid 2.0 assessment for Auction House

## What Solid 2.0 solves

Solid 2.0 became stable on November 16, 2026. Solid runs a component function once and tracks dependencies at reactive reads, so a signal update can update the DOM expressions that read it. The 2.0 release adds async work to the same dependency graph. The result of a promise-returning memo can feed downstream computations directly. Solid can hold a group of related updates until the new values are ready and discard a superseded result that comes back late. In a native Solid UI, `Loading` and `Errored` handle first-load and read failures while `isPending` and `latest` let the UI acknowledge work in flight. [Solid 2.0 release announcement](https://www.solidjs.com/blog/solid-2-0-the-long-hold/) · [Async reactivity guide](https://docs.solidjs.com/concepts/async-reactivity/)

Solid 2.0 also has actions for coordinating async mutations and optimistic stores for temporary overlays. Those mechanisms can display a pending bid and reconcile it with the eventual server result. Auction correctness would still depend on the server establishing bid order, checking the current price and auction status, and handling retries. The proof of concept exercises async reads on the Foundation catalog. [Solid mutation guide](https://docs.solidjs.com/concepts/mutations/)

## Why catalog search is the test case

Foundation starts with six illustrative lots, a synchronous in-memory filter, and a full-page search submit. The toughest relevant problem emerges if searches run against a remote catalog while the user submits successive queries. A slow response for an earlier query can overwrite a later one, the heading and results can disagree, and an empty result can be confused with a failed request. This is a deliberately harder version of the existing search, using the same sample data. The six-lot catalog has no demonstrated performance problem that would justify async search on its own.

The experiment uses the `@solidjs/signals` 2.0.0 package behind the React UI. A Fastify endpoint searches the sample catalog, and the Solid graph coordinates request and result state. A React effect owns the search session, disposes it on unmount, and receives typed snapshots through a callback. Every search gets a fresh request identity, including retries of the same query. The heading and results share one snapshot, and the graph publishes a pending state while the current request is unresolved. This exercises the reactive core while preserving the React/Vite and Fastify stack. Native Solid JSX rendering, Solid server functions, and optimistic writes are outside the experiment. [Published signals package](https://www.npmjs.com/package/@solidjs/signals/v/2.0.0) · [React effect lifecycle](https://react.dev/reference/react/useEffect)

## Grades

Each category is scored out of five. Five means fewer API decisions, stronger types, easier tests, less application branching, clearer documentation, or less deployment work, respectively.

| Criterion | Grade | Rationale |
| --- | --- | --- |
| API nuance | 2/5 | One async memo covers derivation and selection of the latest result. An agent still has to choose which reads can wait or show immediately, track dependencies before the first `await`, understand the two phases of `createEffect`, and dispose the Solid owner through a React effect lifecycle. [Reactivity guide](https://docs.solidjs.com/concepts/reactivity/) · [Async reactivity guide](https://docs.solidjs.com/concepts/async-reactivity/) |
| Type safety | 4/5 | A memo preserves the resolved value's TypeScript type across derivations. The type of the accessor cannot show whether a read can suspend or whether a dependency was tracked. The HTTP response still needs boundary validation. [Memo reference](https://docs.solidjs.com/reference/solid-js/reactivity/create-memo/) · [Post-await diagnostic](https://docs.solidjs.com/reference/solid-js/diagnostics/untracked-read-after-await/) |
| Ease of testing | 4/5 | The signals graph can be exercised without rendering. Controlled promises let tests release requests in a chosen order. `flush()` drains queued reactive work, while network settlement needs a separate await. Browser verification still has to exercise the React lifecycle and visible states. [Testing guide](https://docs.solidjs.com/guides/testing/) · [Flush reference](https://docs.solidjs.com/reference/solid-js/reactivity/flush/) |
| Cyclomatic complexity | 3/5 | Solid can eliminate a hand-written stale-response guard. The experiment delegates rejection of obsolete completions to Solid. The snapshot still takes one explicit pending-or-completed branch by request identity, and four UI outcomes still need handling. A React effect can use one cancellation guard when publishing the result and explicit pending state. There is no demonstrated net branch reduction for this flow. [Async request cleanup](https://docs.solidjs.com/concepts/async-reactivity/#stop-the-work-a-run-started) · [React effect lifecycle](https://react.dev/reference/react/useEffect) |
| Documentation | 4/5 | The 2.0 guides explain held updates, testing, diagnostics, and the migration from React. Packaged diagnostics guides give agents concrete fixes for reactive mistakes. Search can surface older 1.x examples with different effect signatures, and the primary guides concentrate on Solid-owned UI, so this React integration requires joining the Solid and React contracts. [Solid 2.0 docs](https://docs.solidjs.com/) · [Solid for AI tools](https://docs.solidjs.com/guides/ai-tools/) · [From React](https://docs.solidjs.com/migration/from-react/) |
| Deployment | 4/5 | The experiment adds a pinned browser dependency and a relative API request. The production web host needs to serve the new Vite build and route `/api` to the corresponding Fastify build. The search API returns slugs from the same static catalog as the Vite client, so release both together and keep the catalog module in the API artifact if it is packaged separately. The published signals package declares Node `>=22.12.0`, which matters for environments installing the dependency. There is no new service, database migration, or Solid server runtime in this configuration. [Published package manifest](https://registry.npmjs.org/@solidjs%2fsignals/2.0.0) |

## Recommendation

Keep the current synchronous Foundation search. Solid's strongest argument here is its ability to commit a consistent view across several dependent async reads. For a single remote result list, a small React implementation can explicitly abort superseded requests, guard against late responses, and render pending and failure states. A dedicated reactive runtime and its adapter add more concepts for maintainers and agents. Reconsider Solid when a real auction screen needs several dependent requests or coordinated live updates and a like-for-like implementation can demonstrate less application code or fewer consistency defects. [React data-fetching race example](https://react.dev/reference/react/useEffect#fetching-data-with-effects) · [Solid async reactivity guide](https://docs.solidjs.com/concepts/async-reactivity/)


## Verification

- Ran database preparation and migrations, both TypeScript project checks, and the five tests in `npm test`. The proxy returned HTTP 200 for `/api/health` with `ok: true`, `db: 'ok'`, and matching request ID header and body.
- The unit suite controlled response order and used a loader that ignored abort. The new result stayed visible after the old promise resolved. It also verified disposal aborts active work and failure can be retried into an empty result. The Fastify tests exercised query validation, trimming, case-insensitive matching, and catalog ordering.
- Verified the production bundle in headed Chrome. Covered the six initial results, the pending state, overlapping requests, Back and Forward, empty results, a forced HTTP 503 and retry, item links, missing items, direct query URLs, and a 390 px viewport.
- Vite reported 82.33 kB gzip JavaScript for the experiment and 66.21 kB for the committed baseline, a 16.12 kB increase for the entire proof of concept. Both builds used Vite 7.3.6 and the same dependency installation. This measures build output size and includes the search UI and adapter. It does not measure runtime performance.

To review locally, run `npm start` from Part 1 and open `http://localhost:5101/search`. Search for **GPU**, then **Memory**, and use Back to recover the GPU results. Enter an unknown term to see the empty state.
